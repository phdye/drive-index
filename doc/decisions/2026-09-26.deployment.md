# Deployment

Accepted 2026-09-26. Proposal: `doc/proposal/install-and-deployment.md`.
Classification: two-way door — a copy and some symlinks, with the previous
state tagged. Reverting means copying back.

## What was decided

`install --into DIR` places the program in DIR and creates every symlink the
config names beside it. The repository is the source of record; `~/.local/bin`
is where it runs from. Deployment is one command at a moment somebody chose:

    drive-index --into ~/.local/bin install

Without `--into` the old behaviour stands — links beside the running copy —
so nothing that worked before needed changing.

## Why not an existing deployment tool

The proposal made this conditional: use a general deployment tool if one on
the machine already covered it. One did exist, and it did not fit, for two
reasons worth recording because they generalise.

It refused any destination outside a configuration home — `.local/bin`,
`.config` and the like — on the grounds that anything else is somebody's
preference rather than a convention. The original deployment target was
exactly such a preference, so it was one the machine's own tooling would
reject. That judgement was right and the target moved to `~/.local/bin` to
match it.

Its table of what-goes-where was embedded in the script and validated against
a single source repository, so a second repository using it would have meant
copying several hundred lines. A forked tool is a known way to end up with
two implementations that drift and no one noticing which is authoritative.

So its conclusion is followed and only its mechanism differs. The symlink set
here is computed from configuration rather than fixed in a table, `install`
already knew how to compute it, and `--into` is the small addition that lets
it compute it somewhere else.

## What the copy is protected against

Placed through a temporary and renamed, so a run interrupted mid-copy leaves
the old program or the new one and never half of either. That is the same
reasoning as an index build and for the same reason: what is being replaced
is in use.

A destination byte-identical to the source is left alone and a drifted one is
replaced, so a second deployment reports nothing and a deployment after a fix
carries the fix. Both are in the bar.

## The move

The program, the bar and seventeen symlinks had been living in a directory on
PATH, all tracked in that directory's own repository. All of it moved here;
that directory's `.gitignore` now says where the program lives, and its state
before the move is tagged.

Three drive letters — `x`, `y` and `z` — had symlinks there and no config
section, since a single letter needs none. A bare `install` would not have
recreated them, so they were named explicitly. A label that exists only as a
symlink is invisible to a bare install, which is worth knowing before the
next move.

## Why this was worth doing

Two copies with no named moment of deployment drifted twice in one sitting. A
fix made in one copy was overwritten by an older version of the other, and a
regression test — the one covering the defect that started this project —
existed in one bar and silently never ran from the other. Both were found by
accident rather than by a check.
