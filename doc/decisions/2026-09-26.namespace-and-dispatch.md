# The label namespace, and three defects in it

Recorded 2026-09-26. No proposal: these were repairs, found by writing the
first real configuration rather than by review.

## Single letters belong to drives

A one-letter label is a drive and needs no configuration: root `/<letter>/`,
database from `db_file_model`. Anything else must have a section before it
will run.

That guarantee is only worth having if nothing can quietly take a letter, so
two things are refused when the config is read: a one-letter alias, which
would shadow a drive, and a duplicate alias, which would make the index
reached depend on the order sections happened to be parsed in.

## A label may share a name with an admin verb

`install` is a plausible name for a tree and turned out to be one in use.
The admin verbs were tested before the second word, so `drive-index install
locate foo` parsed as the verb with stray arguments and the tree was
unreachable by that spelling.

The second word decides now: followed by an action, the first word is a
label; otherwise it is the verb. Nothing is ambiguous, because the admin
verbs take labels and never actions.

## An alias needs a symlink of its own

`install` made a pair of symlinks for each section and none for its aliases,
so an alias was reachable only by spelling it out as an argument — the form
nobody uses, and not what an alias is written for. Aliases and groups now get
the same pair a section does.

## A guard that stopped working when a default was configured

The check refusing an unknown non-drive label asked whether `root` and
`database` had both fallen through to their built-in defaults.

That was provenance standing in for a fact, and it broke the moment
`db_file_model` appeared in `[defaults]`: every value then had a config
provenance, so an unknown label passed the guard and failed much later as a
missing index — three layers from the actual mistake.

It asks the sections directly now. An explicit `--root` or `--db` is still
enough on its own, which is what lets a one-off label be searched without
writing a section for it.

The general lesson is the one worth keeping: where a value came from is the
right thing to *report* and the wrong thing to *test*, because adding an
unrelated default silently changes the answer.

## Wrapping locate does not mean narrowing it

An early version enumerated four of `locate`'s options and rejected the rest,
so `-r`, `-b`, `-w`, `-A`, `-p` and the follow flags were all unreachable.
Unknown options are passed through untouched now, and `locate` rejects what
it does not know in its own words.

Two consequences fell out of that:

`--all` was renamed `--all-indexes`, because it had been shadowing `locate`'s
own `--all`. A wrapper should not take a name from the tool it wraps.

`locate` exits 1 both for "nothing matched" and for a mistyped option, so a
typo read as an empty result. Having complained while producing nothing
distinguishes them. Reading its error text would have worked and would not
have survived a different locale, so that was rejected in favour of the
behavioural signal.
