# Groups

Accepted 2026-09-26. Proposal: `doc/proposal/groups.md`.
Classification: two-way door — a config section and an indirection, with no
stored state and nothing to migrate. Reverting means deleting the sections.

## What was decided

A `[group.<name>]` section reaches several labels under one name, narrowed by
`--<selector>` options declared as `member.<selector> = <label>`. Both verbs
default to every member. Selectors union. Build order is config order.

A group is an indirection and never an index, so `status`, `bulk`, the
metadata sidecars and the atomicity guard needed no second code path.

## Why all members, for both verbs

An earlier draft had `updatedb` default to one member, arguing that a sweep
might rebuild the wrong environment. That reasoning was wrong: indexing reads
a root and writes the index to local storage, so building more than was meant
costs time and read load, not damage, and the collapse guard already protects
the index being replaced.

The asymmetric risk runs the other way. Searching one environment while
believing all three were searched produces a finding about the wrong system,
and nothing in the output says so. Hence widening is the silent default and
narrowing is announced: when a selector resolves a group to fewer than all its
members, the members searched are named at normal verbosity, on stderr, where
they stay out of piped output but survive into a pasted transcript.

## Validation at load

Six refusals, each with its own reason, all raised when the file is read:

- a selector matching an option of this program, which would be consumed
  before the group was known
- a selector matching an option of `locate`, which would be taken from it
- a member naming another group; groups do not nest
- a member naming something that is neither a drive letter nor a section
- a member named twice, which would build it twice and report every hit twice
- a group name that is a single letter, a label, or an alias

The two option sets are not hand-listed. This program's come from the parser
itself, so a new option cannot be added without the check learning about it
the same day; `locate`'s were read from `locate --help` on findutils 4.11.0
and are a constant, spelled out because the usage line collapses `--existing`
and `--non-existing` into one token.

## The defect found while implementing

`argparse` matches positionals in one contiguous run, so everything after the
first unrecognized option lands in the leftovers — patterns included. Through
a symlink there are no leading positionals and it never showed. Through
`drive-index area locate --prod PATTERN` the pattern vanished and the run
reported having nothing to look for.

Leftovers that are not options are folded back into the words. That is sound
here because the only two options of `locate`'s taking a separate value are
owned by this program, so a leftover that does not start with a dash cannot
be somebody's argument.

## Not done

Groups whose members are subtrees of one drive will want the searched label
printed alongside each hit. The group's members are separate mounts, so a hit
self-identifies by path — that is luck, not design, and the first group built
the other way will need it.
